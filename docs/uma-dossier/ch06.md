# Chapter 06 — Shader Translation and SIMT Execution: From RDNA2 Wave64 to 32-Wide Host Warps

> Scope. This chapter explains why ~430 of the title's console shaders still fail to translate, why that failure — not
> memory bandwidth — is what keeps the final picture black, and which compiler techniques from the research literature
> and from production translators can close each gap. It also covers the performance cost of executing RDNA2 wave64 code
> on NVIDIA's 32-wide warps, and what that means for the frame-time budget measured in the other chapters.
>
> Conventions. Facts carry a reference [n]. Measurements come from our own VIctory runs on an RTX 3080 (10 GB) +
> i5-10400F, Series S profile (1280x720 internal), builds `test13`–`test15` of 24 Nov 2026. Hypotheses are labelled
> **H-6.n**. VIctory source locations are given as `crate/file:line` against the `test15` branch.

## 1. Why shader translation is on the critical path for the black screen

Chapter 01 and Chapter 02 treat the black world as a memory-coherence problem. Render-target dumps taken on 24 Nov 2026
(run56, frame 2950, 229 targets) show that this is only half the story:

| Target class (1280x720 unless noted) | Content in the dump | Interpretation |
|---|---|---|
| G-buffer colour/normal targets (DXGI formats 24, 28) | picnic tables, a street lamp, pedestrians, power lines | geometry passes run and write correct data |
| Masks/stencil-like targets (formats 49, 54, 62) | same silhouettes | geometry passes run |
| Lighting / HDR accumulation (formats 10, 26, 42, 61) | all zero | the passes that should write them never ran |
| Final 1920x1080 output (formats 24, 28) | uninitialised memory (noise) | nothing composes the final image |

The passes that fill the lighting and HDR targets are almost all compute dispatches. When a compute shader does not
translate, VIctory drops every dispatch that uses it (`victory-gpu/src/pipeline.rs`, "shader does not translate; its
pipelines' draws are dropped"). The world is therefore black for a compiler reason: the shading, lighting, tonemapping and
composition programs are missing, so the G-buffer is never resolved into a picture. The same diagnosis has been reached
independently by other contributors (VIctory PR #638 shows the G-buffer through `VICTORY_SHOW_TARGET=busiest`; issue
#71 reports uniform HDR targets on an RTX 5090).

Five of the six largest groups are about **SIMT semantics** — how the console's wave executes divergent code and how lane
masks are used as data — not about memory. That is the subject of this chapter.

## 2. Background: how RDNA2 executes a shader

### 2.1 Waves, lanes and the two register files

RDNA2 (GFX10.3) executes shaders in *waves* of 32 or 64 work-items ("lanes") [1][2]. Each lane has its own vector
general-purpose registers (VGPRs); the wave as a whole shares scalar registers (SGPRs). Scalar instructions (`s_*`) run
once per wave on the scalar unit; vector instructions (`v_*`) run for every lane whose bit is set in the execution mask
`EXEC` [1]. Wave64 is executed by RDNA2 hardware as two passes of a 32-wide SIMD (or, for some instruction classes, by
dual-issue), but architecturally it is one wave with a 64-bit `EXEC` and 64-bit lane masks [1][2].

Key architectural objects for this chapter:

- **`EXEC`** — 32 or 64 bits, one per lane; a vector instruction writes only lanes whose bit is 1.
- **`VCC`** — the vector condition code, a lane mask written by vector compares (`v_cmp_*`).
- **Lane masks in SGPR pairs** — any SGPR pair can hold a 64-bit lane mask; compares can write them (VOP3 form), and
  scalar ALU instructions (`s_and_b64`, `s_or_b64`, `s_andn2_b64`, `s_xor_b64`, `s_not_b64`, `s_cselect_b64`, …)
  combine them like ordinary integers.
- **`SCC`** — the scalar condition code (one bit per wave).
- **Cross-lane operations** — `v_readlane_b32`, `v_readfirstlane_b32`, `v_writelane_b32`, DPP (data-parallel primitives,
  lane permutes inside rows of 16), `v_permlane16_b32`/`v_permlanex16_b32`, `ds_swizzle_b32`, `ds_bpermute_b32` [1].

### 2.2 Control flow is explicit mask arithmetic

The most important difference from a host shading language: **RDNA2 has no structured `if/else` in hardware**. A
compiler lowers divergent control flow to mask manipulation and scalar branches [1][3]:

```
; if (x > 0) { A } else { B }      — typical RDNA2 lowering (illustrative, not title code)
v_cmp_gt_i32   vcc, 0, v0          ; vcc = lanes where x > 0
s_and_saveexec_b64 s[2:3], vcc     ; s[2:3] = old exec ; exec &= vcc
s_cbranch_execz  ELSE              ; skip A if no lane takes it
  ... A ...
ELSE:
s_andn2_b64    exec, s[2:3], exec  ; exec = old exec & ~(lanes that ran A)
s_cbranch_execz  JOIN
  ... B ...
JOIN:
s_or_b64       exec, exec, s[2:3]  ; restore
```

Every one of those masks is an ordinary 64-bit integer in SGPRs. Nothing stops a program — or the console's compiler —
from storing such a mask to memory, shifting it, counting its bits, selecting on it, or comparing it with another mask.
The console shader compiler does exactly that when it optimises: it reuses masks across regions, keeps masks alive across
loops, and turns "lanes that are active here" into data for ballots and compaction.

### 2.3 What a host shader model offers

DXIL (the LLVM-based IR that D3D12 consumes) and HLSL Shader Model 6.x expose *wave intrinsics* — `WaveReadLaneFirst`,
`WaveReadLaneAt`, `WaveActiveBallot`, `WaveActiveSum`, `WavePrefixCountBits`, `QuadReadAcrossX`, … — but **no explicit
EXEC register** [4][5][6]. Control flow is *structured* (if/else, loops, switch) and the set of active lanes is implicit:
it is whatever the host compiler and hardware decide at that point of the structured program. Shader Model 6.6 added
`[WaveSize(N)]` to request a wave width for compute shaders on hardware that supports several widths [7]; NVIDIA hardware
only offers 32 [8][9].

So a translator must turn *mask arithmetic over explicit registers* into *structured control flow over implicit masks*,
and must emulate wave64 semantics (64-bit masks, `v_readlane` across 64 lanes, ballots of 64 bits) on 32-wide warps when
the host is NVIDIA.

## 3. The literature: divergence, reconvergence and uniformity

The problems VIctory hits have been studied for two decades, mostly from the hardware side (how should a SIMT machine
handle divergence?) and from the compiler side (which values are provably the same in every lane?).

### 3.1 SIMT reconvergence

- **Dynamic Warp Formation** (Fung, Sham, Yuan, Aamodt, MICRO 2007) [10] showed that the immediate-post-dominator
  reconvergence stack loses a large share of SIMD efficiency on divergent code and proposed regrouping threads that take
  the same branch into new warps. **Thread Block Compaction** (Fung & Aamodt, HPCA 2011) [11] made the regrouping
  practical at the thread-block level.
- **Stack-less reconvergence** (Collange, 2011) [12] replaced the reconvergence stack with per-thread program counters and
  a min-PC selection policy — the same "per-lane PC" model that NVIDIA's Volta later exposed as *independent thread
  scheduling* [8].
- **MIMD synchronization on SIMT** (ElTantawy & Aamodt, MICRO 2016) [13] studied deadlocks caused by inter-thread
  synchronization inside divergent SIMT code — directly relevant to the console's barriers and spin loops (Chapter 07).

Relevance: the console's code was compiled for a stack-free, mask-explicit machine (RDNA). The host is either a
stack-based or an independent-thread-scheduling machine (NVIDIA since Volta [8]). A translator that reconstructs
structured control flow is implicitly choosing the host's reconvergence points; wherever the console relied on its own
(explicit) reconvergence — e.g. reading a mask computed before a branch after the branch — the translator must prove the
two agree or emulate the console mask explicitly.

### 3.2 Uniformity (divergence) analysis

- **Divergence Analysis and Optimizations** (Coutinho, Sampaio, Pereira, Meira, PACT 2011) [14] and its journal version
  **Divergence Analysis** (Sampaio, Souza, Collange, Pereira, TOPLAS 2013) [15] define the standard static analysis:
  a value is *uniform* if every active lane holds the same value; it is *divergent* if it depends on the lane ID, on
  divergent memory loads, or on a branch whose condition is divergent (through φ-nodes at the join — "sync dependence").
- **Whole-Function Vectorization** (Karrenberg & Hack, CGO 2011) [16] gives the complementary transformation: turning
  scalar control flow into masked vector code, with a precise treatment of which φ-nodes need blending.
- **Convergence and Scalarization for Data-Parallel Architectures** (Lee et al., CGO 2013) [17] shows how much work can be
  moved to scalar units once uniformity is known — the console compiler's own optimisation, which the translator must
  *undo* or *preserve*.

Relevance: VIctory already has a uniformity analysis (`self.uniform`, `structure.rs` `Atom::Uniform`), extended on 24 Nov
2026 with a *wave-uniform value* analysis that accepts `v_readfirstlane` of values built only from SGPRs, literals and
other uniform values (merged in `test13`, ~3,000 dispatches per frame recovered). The literature suggests two further
steps: (a) **sync-dependence-aware uniformity** — a value defined under a uniform branch is still uniform at the join if
the branch condition is uniform [14][15]; (b) **mask-value tracking** — treat lane masks as first-class abstract values
(the "set of lanes for which predicate P held at program point X") and propagate them through scalar mask arithmetic.

### 3.3 Production translators

- **AMD's own compilers** — LLVM's AMDGPU backend [3] and Mesa's ACO [18] — are the inverse of what VIctory does: they
  *produce* EXEC-mask code from structured IR. Their documentation of how `s_and_saveexec`, `s_andn2`, `s_or` and
  `s_cbranch_execz` patterns encode if/else/loops (the "structurizer" and the "exec-mask lowering" passes) is the best map
  of which mask idioms the console's code contains [3][18].
- **XCL** (another Xbox Series recompiler) translates GFX10 to HLSL and compiles with DXC, and reports 100% of a title's
  26,698 shaders translated, with a two-wave32 split for wave64 on 32-lane GPUs and two static analyses (`x64_masks` mask
  liveness and `upper_lanes` tracking) that cut the wave64 emulation overhead on an RTX 3090 from 1.64–1.68x to
  1.04–1.11x in mask-heavy loops (XCL `HANDOFF.md`, sessions on wave64). Unlike VIctory it emits HLSL, so DXC's own
  optimiser and structurizer do part of the work.

## 4. Wave64 on 32-wide warps: what it costs

### 4.1 How VIctory emulates wave64

On NVIDIA (`WaveLaneCountMax == 32`) VIctory selects `Wave64Mode::Wave32` (`victory-gpu/src/host.rs:251-254`): each
console wave64 becomes a *virtual wave* of two host warps that cooperate through group-shared memory (LDS). Cross-lane
operations (`v_readlane`, `v_readfirstlane`, ballots, DPP across the 32-lane boundary) are implemented by writing values
to an LDS exchange area, a group barrier, and reading them back (`emit/lower.rs` `compute_ballot_in_cur`,
`exchange_two_halves`, `emulated_readfirstlane`; LDS reservation `ballot_dwords`/`exchange_dwords`, `lower.rs:1881-1892`).

Consequences:

1. **Barriers.** Each emulated cross-lane operation needs the two halves to meet — a `GroupMemoryBarrierWithGroupSync`.
   A barrier is only legal in *uniform* control flow; in divergent code one half may never arrive. This is why VIctory
   refuses cross-lane operations "in divergent control flow" (`lower.rs:2427`, `:2483`): the refusal is a correctness
   guard, not a missing feature.
2. **LDS pressure.** Exchange buffers take LDS. RDNA2 lets one work-group allocate up to 64 KB of LDS [1], while D3D12
   guarantees 32 KB of group-shared memory per group; a console shader that already uses close to 32 KB cannot also fit
   the exchange buffers, and is refused (`lower.rs:2926-2927`).
3. **Occupancy.** Extra LDS and barriers reduce the number of resident groups per SM.

### 4.2 Measured overhead

We do not yet have per-shader timings for VIctory's emulation. XCL's measurements on an RTX 3090 (from its handoff
notes) give the order of magnitude: naive two-warp emulation 1.64–1.68x the native cost on mask-heavy loops, reduced to
1.04–1.11x after mask-liveness analysis. On AMD RDNA hosts VIctory uses native wave64 (`Wave64Mode::Native`) and pays no
emulation cost [7].

### 4.3 Alternatives to the two-warp scheme

| Scheme | Idea | Pros | Cons |
|---|---|---|---|
| Two warps + LDS exchange (current) | one virtual wave = 2 host warps | exact semantics for 64-lane masks | barriers forbid use in divergent flow; LDS cost |
| One warp, two lanes per thread ("wide lanes") | each host lane runs console lanes *i* and *i+32* | cross-lane ops become intra-warp shuffles + local moves; no barriers | doubles VGPR use; divergence between the two console lanes in a host lane must be serialized |
| Re-compile as wave32 where provably safe | prove the shader never observes lanes 32–63 (no ballots/readlanes crossing 32) | zero overhead | needs whole-program proof; many shaders use 64-bit ballots |
| Split per region | wave32 outside cross-lane regions, two-warp exchange inside uniform regions | best of both | complex |

The "wide lanes" scheme is used by some CPU-side SIMT emulators and by vectorizers that map *k* program instances to one
vector lane [16]; it removes the barrier problem entirely because no other warp has to arrive.

## 5. The six refusal classes, one by one

For each refusal: what the console code is doing, why VIctory refuses, how the literature/production systems handle it,
and a hypothesis with a test.

### 5.1 "a select on an untracked mask" (77 shaders)

*What the code does.* `v_cndmask_b32 vD, vA, vB, s[m:m+1]` selects per lane between two values using a lane mask held in
an SGPR pair (`lower.rs:6420-6426`). VIctory can lower it only when it knows *which predicate* that mask represents
(`self.x.st.masks`): the structurizer records masks created by compares and by its own control-flow reconstruction.
Masks produced by *scalar arithmetic on masks* (`s_and_b64`, `s_andn2_b64`, `s_or_b64` of masks, `s_cselect_b64` between
masks, or a mask computed in one region and consumed after a join) are not tracked, so the select is refused.

*Why it matters.* Selects on combined masks are the bread and butter of optimised console code: "lane is active AND
passed the depth test", "lane hit light *k* OR is the first lane". In the dump these feed tiled-lighting and culling
compute passes.

*How others handle it.* A mask is just a 64-bit integer. If the translator materialises every mask as data — one bit per
lane computed as `WaveActiveBallot(predicate)` at the point of definition, then combined with integer ALU — then
`v_cndmask` becomes `((mask >> laneId) & 1) ? b : a`, which is valid in any control flow and needs no tracking [5][6].
This is the "masks as values" approach of whole-function vectorizers [16].

> **H-6.1 — Materialise lane masks as 64-bit integer values.** Represent every SGPR-pair mask as an integer (two 32-bit
> halves) computed by ballots where it is defined and by integer ALU where it is combined; lower `v_cndmask` on such a mask
> to a bit test of the current lane. *Predicted effect:* most of the 77 shaders translate; any that still fail do so on a
> later stage. *Cost:* one ballot per mask definition (cheap on NVIDIA — a single instruction in uniform control flow;
> requires the exchange in the two-warp scheme). *Risk:* in divergent flow the ballot only sees active lanes, which is
> exactly the console semantics for compares writing masks (inactive lanes write 0 in VOP3 compares [1]). *Test:* count of
> "select on an untracked mask" in the log goes to ~0; render-target dumps show new lighting targets written.

### 5.2 "a lane mask holding lanes elsewhere read as data" (68 shaders)

*What the code does.* A mask that contains lanes *not active at the current point* is read as data — e.g. a mask
computed before a branch (all lanes), then used inside the branch where only some lanes run, typically in a ballot, a
`s_bcnt1` (popcount) to compute a compaction offset, or `s_ff1` (find first lane) to elect a leader (`lower.rs:2630-2637`).

*Why VIctory refuses.* In the two-warp emulation, a ballot computed *here* sees only the active lanes. To return the
console's value it would need the mask as it was *where it was defined*. VIctory tracks masks symbolically and refuses
if the symbol is not "active lanes here".

*How to handle it.* With H-6.1 the mask is already a stored integer — it holds lanes elsewhere by construction. Reading
it as data is then a plain register read. This class should largely disappear with H-6.1.

> **H-6.2 — Masks crossing control-flow joins are SSA integers.** Treat a mask defined in one region and used in another
> as an ordinary SSA integer (two `i32`s). *Prediction:* the 68 shaders move to "translated" or to another reason.
> *Test:* as H-6.1. *Note:* This is the same change as H-6.1 seen from the consumer side.

### 5.3 "a cross-lane wave operation in divergent control flow" (60 shaders)

*What the code does.* DPP row operations, `v_permlane*`, `ds_swizzle`, `v_readlane` inside a region where not all lanes
are active — common in reductions over "lanes that hit this light" or prefix sums for compaction.

*Why VIctory refuses.* Under the two-warp scheme, crossing the 32-lane boundary needs both halves at a barrier, which is
illegal in divergent flow (`lower.rs:2427`).

*How to handle it.*
1. **Classify by lane distance.** Many of these operations never cross lane 31/32: DPP row operations act within rows of
   16 lanes [1]; `quad_perm` within quads; `row_mirror`/`row_shr` within a row; `v_permlane16` within a 16-lane row.
   Those map to host wave intrinsics *inside one warp* (`WaveReadLaneAt` on lanes of the same half, `QuadReadAcross*`) and
   need no barrier [5][6]. Only `v_permlanex16` (swap between rows), 64-wide `v_readlane` with lane ≥ 32, and 64-bit
   ballots really cross the halves.
2. **Wide lanes for the rest.** With the "one warp, two lanes per thread" scheme (§4.3), crossing becomes a local move.

> **H-6.3 — Intra-half cross-lane ops need no barrier.** Lower DPP/quad/row/`permlane16` operations to host wave
> intrinsics within the warp when the access pattern provably stays inside 32 lanes, and allow them in divergent flow
> (inactive source lanes read as the console defines: DPP `bound_ctrl` semantics [1]). *Prediction:* a majority of the 60
> shaders translate. *Test:* add a log of the operation kind at the refusal site first (diagnostics) to measure how many
> refusals are intra-row; then implement.

### 5.4 "a structured buffer of unknown stride" (41 shaders)

*What the code does.* A buffer descriptor (V#) whose stride field is 0 or not a multiple of 4 is used with indexed
loads (`lower.rs:8558-8564`). On RDNA a V# with stride 0 and `idxen` addresses `base + offset` only, and raw/byte access is
legal [1].

*How to handle it.* Read the same bytes through a raw (`ByteAddressBuffer`) view and compute addresses in the shader;
this is exactly what open VIctory PR #704 ("unknown-stride buffers are read through a raw view of the same bytes")
proposes.

> **H-6.4 — Merge PR #704 (raw view for unknown strides).** *Prediction:* most of the 41 shaders translate. *Test:*
> count drops; no new GPU faults in DRED.

### 5.5 "v_readfirstlane in divergent control flow" (37 shaders remaining)

The wave-uniform case is done (`test13`). The remaining uses read a genuinely lane-varying value — the classic
"scalarization loop" (waterfall): pick the first active lane's descriptor index, run the body for all lanes with that
index, remove them, repeat [17]. VIctory `main` gained explicit waterfall-loop support on 24 Nov 2026 ("Shaders: the
console's waterfall loop over a first-lane table offset", "lower waterfall loops over per-lane descriptors in one pass").

> **H-6.5 — Rebase onto current `main` for waterfall loops.** *Prediction:* a part of the 37 is already handled upstream.
> *Test:* rebase `test15` onto `origin/main`, recount.

### 5.6 "an address not from a root parameter" (29 shaders)

Addresses computed from memory loaded through another pointer (pointer chasing: a table of buffer addresses read from a
constant buffer) or from arithmetic the tracker cannot resolve. This class needs a *generic* memory model on the GPU —
the "flat memory window" approach of XCL (`mem` UAV over title memory, Chapter 04) — so that any 64-bit address can be
dereferenced. It is the shader-side counterpart of the zero-copy hypotheses in Chapters 03–04.

> **H-6.6 — A flat-memory fallback for untraceable addresses.** Bind a raw UAV that spans the title's GPU-visible memory
> windows; translate an untraceable 64-bit address into a window index plus offset. *Prediction:* the 29 shaders
> translate; performance of those accesses is that of whatever memory backs the window (system memory over PCIe unless
> mirrored in VRAM). *Dependency:* Chapter 04 (window design).

## 6. Loops, termination and GPU hangs

### 6.1 The observation

On NVIDIA, the world reliably removes the device (DXGI_ERROR_DEVICE_HUNG, `0x887A0006`) within minutes. DRED breadcrumbs
in our runs stop at the same mesh pipeline pair (`mesh 04b9be3756e8f41c` + `pixel 1af4a50c7fb40c97`), and an RDNA4
contributor measured the same pair at 90–348 ms *per draw* of 4–39 mesh groups (VIctory issue #71). Offline disassembly
of the two programs (done locally; no title code is reproduced here) showed:

- the mesh program contains **no backward branch** (no loop at all);
- the pixel program is a clustered-lighting shader with nested loops over light lists, whose outer loop **exits on an
  equality test** between a running index and a bound read from a buffer, and whose inner loop iterates a bitmask.

An equality-terminated loop is safe when the bound is valid. If the bound comes from a buffer that a dropped
(untranslated) compute pass was supposed to fill, it can be zero or garbage, and the index never meets it. With VIctory's
default per-loop iteration cap of 2^20 (`emit/lower.rs`, `LOOP_LIMIT`) per lane and per loop entry, nested loops over
millions of pixels exceed any watchdog.

### 6.2 What we measured

| Run | Loop cap | Result |
|---|---|---|
| run41 (Series X) | default 2^20 everywhere | hang at ~400 s in the pair above |
| run42/43 | 4,096 / 65,536 everywhere | the title itself faults during loading (~90 s) |
| run45 | 256 only on `1af4a50c…` | that pair leaves the hung submissions; the hang moves elsewhere |
| run47/51 (Series X), run53 (Series S) | 1,024 on pixel, mesh and vertex stages only | **no hang for 17+ minutes**, gameplay HUD reached |
| run54 (Series S, + PR #493) | default | hang again at ~300 s in the same pair |
| run57/58 (`test15`, more compute translated) | 1,024 graphics (+ 262,144 compute in run58) | hang at ~200 s: newly translated compute adds new long-running work |

So: (1) runs that changed the loop cap for compute crashed during loading — but see §6.4: every such run also started
with a cold or bypassed shader cache, which is the more likely cause; (2) a low cap on *graphics* loops is harmless to what we can observe today and prevents
hangs; (3) PR #493 (bounding root SRV reads to the buffer's host copy), which removed the hang for another contributor on
an RTX 4090, is not sufficient here; (4) each step that translates more compute exposes new long-running work, which is
consistent with H-6.7 below.

### 6.3 Interpretation

Iteration caps are a robustness device, not a fix. The root cause is a *data dependency on a pass that did not run*. The
correct fixes are: translate the producer (§5) or, while a producer is missing, make consumers see a *safe* value — for
example zero-initialise the buffers a dropped dispatch would have written. VIctory PR #638 adds exactly the diagnostics
for this (`VICTORY_PRODUCERS=1`: for every dropped dispatch, remember the ranges it would have written and report later
readers). The deadlock literature on SIMT machines [13] is relevant for the remaining case of spin-waits between groups.

> **H-6.7 — Hangs come from consumers of dropped producers.** *Statement:* every remaining long-running graphics loop
> reads a buffer range that an untranslated compute dispatch should have written in the same frame. *Test:* merge #638,
> run with `VICTORY_PRODUCERS=1`, list (reader, dropped producer) pairs for the pipelines in hung submissions.
> *Prediction:* each hung pipeline maps to at least one dropped producer; translating those producers removes the hang
> without any loop cap.

> **H-6.8 — Zero-fill what dropped producers would have written.** *Statement:* until producers translate, filling their
> output ranges with zeros at the point of the drop makes equality-terminated loops exit (index 0 equals bound 0) and makes
> lighting contributions vanish instead of hanging. *Test:* with H-6.7's map, clear the ranges; run without loop caps.
> *Risk:* other undefined-but-finite behaviour; strictly a diagnostic mode.

> **H-6.9 — Stage-specific loop caps as a supported safety net.** *Statement:* a cap of ~1,024 iterations on
> pixel/mesh/vertex stages (never compute) is a pragmatic safety net for NVIDIA users until H-6.7 is resolved.
> *Evidence:* runs 47/51/53. *Cost:* our diagnostics switch (`VICTORY_LOOP_LIMIT_SHADERS=ps:1024,ms:1024,vs:1024`)
> translates those stages without the shader cache, adding translation time at load.

### 6.4 Two further causes reported by the XCL author, checked against our data

On 24 Nov 2026 the XCL author reported on the community Discord that the black screen after loading has two causes:
(a) on first launch, shader compilation freezes rendering long enough for the game to decide it hung and close; it gets
better once shaders are cached; (b) the GPU ends up waiting on itself in the wrong order, so the game draws from data that
was never written. We checked both against VIctory's code and our runs.

**(a) Cold shader cache trips the title's watchdog.** VIctory's shader cache key includes the loop limit
(`victory-gpu/src/shader_cache.rs`, `build()`), and our per-stage caps bypass the cache entirely. Every run that crashed
during loading — run42 and run43 (global caps 4,096 and 65,536), run59 (per-stage caps with DRED) — therefore re-translated
every shader. All three crashed at the same address (`+0x164a298`), with a call stack through the title's watchdog thread
(`+0x2215eca`). Our earlier conclusion that "a low compute loop cap breaks the game" is better explained by the cold
cache. The watchdog patch we use (`2215c70`) disables only one of the watchdog's paths.

> **H-6.13 — Warm the cache before measuring; translate off the render thread.** *Statement:* loading-time crashes at
> `+0x164a298` are watchdog terminations caused by translation stalls on a cold cache. *Test:* run once with a fixed
> configuration to fill the cache, then repeat the same configuration; the crash should disappear on the second run.
> Long term: translate asynchronously and draw nothing (or a stub) until a pipeline is ready, as XCL does.

**(b) Queue waits are not honoured.** In VIctory, `ID3D12CommandQueue::Wait` returns immediately without blocking
(`victory-gpu/src/queue.rs`, `wait`: "Nothing runs on the queue, so waiting for a fence never blocks it"), and
`ExecuteCommandLists` runs and waits for the lists synchronously at the moment it is called (`execute`). If the title
submits on its compute queue `Wait(fence, N)` followed by a consumer, and expects another queue to produce data and signal
`N` later, VIctory runs the consumer *before* the producer. The consumer reads memory that was never written: lighting
reads empty buffers (black picture) and equality-terminated loops see invalid bounds (GPU hang, §6.1). This also explains
why each step that translated more compute work exposed a new hang: more consumers ran, out of order.

> **H-6.14 — Honour GPU-side queue waits.** *Statement:* deferring a queue's later submissions (lists and signals) until
> the awaited fence reaches its value, and flushing them in order when another queue or the CPU signals it, removes both
> the black lighting targets and the hangs. *Test:* implement per-queue pending lists in `queue.rs`/`fence.rs`; run
> without loop caps; dump world render targets. *Risk:* deadlock if the CPU waits on a fence that only deferred work
> signals — the CPU wait must flush pending work first. *Relation:* refines H-6.7 — the "dropped producer" may in many
> cases be a producer that ran *after* its consumer.

## 7. Mesh shaders and NGG

RDNA2 implements mesh shading on its NGG (next-generation geometry) pipeline: one lane sends an allocation request
(`s_sendmsg GS_ALLOC_REQ`) with the vertex and primitive counts, then lanes export positions, parameters and primitive
connectivity [1]. D3D12 mesh shaders instead require `SetMeshOutputCounts(v, p)` to be called once, in uniform control
flow, before any output write [19].

VIctory's mesh prologue (`emit/lower.rs`, `mesh_prologue`) declares the maximum counts up front and culls unused
primitives, and removes barriers dominated by the allocation request (one lane runs that region alone, so a barrier there
would deadlock on the host). PR #587 additionally guards output indices and omits group sync for barriers in divergent
regions. Remaining refusals involve mesh programs whose shape the prologue cannot express (non-triangle topologies, or
counts beyond the host limits of 256 vertices, 256 primitives and 128 threads).

> **H-6.10 — Two-pass mesh fallback.** For mesh programs beyond host limits, run the console program as a compute shader
> that writes vertices and indices to a buffer, then draw with a pass-through mesh or vertex shader. XCL uses this pattern
> for NGG ("2-pass CS + passthrough"). *Prediction:* recovers the remaining mesh refusals; the cost is an extra buffer
> round trip in VRAM.

## 8. How the translator emits code, and why it matters for coverage

VIctory emits DXIL bitcode directly (`victory-shader/src/emit/bitcode.rs`) and validates it with `dxil.dll`. XCL emits
HLSL and compiles it with DXC. Trade-offs:

| Aspect | Direct DXIL (VIctory) | HLSL + DXC (XCL) |
|---|---|---|
| Control | exact instruction selection, no compiler surprises | DXC may restructure; harder to guarantee console semantics |
| Optimisation | must be done by the translator | DXC/LLVM optimisations for free |
| Structurization | translator must produce a structured CFG | translator emits loops with flags; DXC structurizes |
| Development speed | slower; each new construct needs bitcode emission | faster; HLSL is easy to extend |
| Debuggability | bitcode is opaque | generated HLSL is readable |
| Coverage reported | 430 refusals remaining (this title) | 100% of a different title's corpus |

> **H-6.11 — A generic slow path per region.** When a region cannot be translated precisely, emit a conservative per-lane
> interpreter loop for that region (lanes serialized, masks as integers, memory through the flat window). *Prediction:*
> coverage near 100%, with a performance penalty limited to the affected regions. *Risk:* high; the interpreter must match
> the ISA exactly [1].

## 9. Performance after translation

Even with every shader translated, translated code is slower than the console's native code:

| Source | Mechanism | Mitigation | References |
|---|---|---|---|
| Wave64 emulation on 32-wide warps | barriers + LDS exchange | mask liveness (XCL `x64_masks`), wide-lane scheme | [8][9] |
| Scalar-to-vector demotion | SGPR values become per-lane values | uniformity analysis keeps them uniform | [14][15][17] |
| Structured CFG reconstruction | duplicated blocks, flag variables | better structurization | [3][18] |
| Bounds and robustness checks | guards on descriptors and outputs | remove where proven in range | — |
| Console-only hardware features | DCC, HTILE, fast clears are host-driver decisions | none on PC (driver-managed) | [2] |

> **H-6.12 — Native wave64 on AMD hosts as a reference point.** Running the same build on an RDNA2/3 GPU (native wave64)
> isolates the emulation cost: the GPU-ms difference against an NVIDIA run, normalised by raw throughput, estimates what
> H-6.1–H-6.3 can still save on NVIDIA. *Test:* one run on any RDNA2+ card with the same profile and capture frames.

## 11. Chapter conclusions

1. The black world is primarily a **coverage** problem: geometry is drawn; lighting and composition passes are refused.
2. Five of the six largest refusal classes are about **SIMT mask semantics**. The literature's answer — treat masks as
   values, analyse uniformity including sync dependence, keep cross-lane operations within the host warp where possible —
   maps directly onto VIctory's refusal sites (H-6.1–H-6.3).
3. GPU hangs on NVIDIA are best explained as **consumers reading data their producers have not written** — because the
   producer was dropped (H-6.7) or because queue waits are ignored and it ran later (H-6.14). Stage-specific loop caps are
   a measured, working safety net; the fixes are honouring queue waits and translating the producers.
4. Open PRs already cover parts of the gap (#704 unknown strides, #638 producer tracking, #587 mesh guards, waterfall loops
   on `main`); combining them with the hypotheses here is the shortest path to a lit frame.
5. Loading-time crashes after configuration changes are cold-cache watchdog terminations (H-6.13), not an effect of loop
   caps on compute.
